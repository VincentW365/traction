## A. Objective

Resolve, as one focused remediation, the defects observed on the deployed site: customer/vehicle search, missing inspection templates, undelivered email, customer links that only work on the LAN, an appointment wizard that cannot go back, customer booking gaps (3 PM cutoff, service-request capture, shared engine parity, WhatsApp hand-off), and the SharePoint historical-data carry-over. Every fix is at the logic/configuration/data level, carries regression coverage, and must survive a clean deployment.

## B. Inputs used

Six read-only investigations (2026-09-15) with `file:line` evidence, live probes against `bsop_dev` (6,901 customers / 8,290 vehicles) and a fresh deployed-equivalent database `bsop_golive_probe` (migrate → seed → deploy-check); `CLAUDE.md`; `docs/03` (SCH/ARR/NOT/GOV rules); `docs/21`; `docs/108`, `docs/119` (parity); `docs/110` (notifications); `docs/120` (booking + ETA); `DEPLOYMENT.md`, `DEPLOY_RENDER.md`, `docs/DEPLOYMENT_HANDOFF.md`, `AGENTS.md`; `render.yaml`.

## C. Root causes (§32 of the CR) — why each defect existed

### C1. Search — why first name worked while full name / phone / registration failed
- **RC1 No tokenised name matching on the endpoints the pickers use.** `GET /customers?q=` (`customers.service.ts:36-55`), the ADMIN directory (`:90-104`, raw SQL) and `GET /vehicles?q=` (`vehicles.service.ts:38-53`) run the **whole string** as one `contains` per column: "Vincent Wilson" is compared against `firstName`, `lastName`, `phone`… separately, and no column ever contains both words → empty. A single first name is a substring of `firstName`, which is why that case worked. Only the topbar global search tokenises (`visits/search.service.ts:50-67`) — and it hard-codes token[0]=firstName + rest=lastName, so reversed order fails and the **1,164 imported customers stored with an empty firstName** (companies, joint owners, single-token names — `customer-vehicle.mapper.ts:127-141`) can never match a two-word query.
- **RC2 Two phone formats and no normalisation on either side.** Imports store digits only (`mapper.ts:68-70`); UI-created customers store the DTO string verbatim with dashes (`customers.service.ts:158`, `:370`; DTO has only `@IsString()`). Queries compare the raw input (`customers.service.ts:40`), so `876-555-1234` misses imported rows and `8765551234` misses UI rows; `+1 876 555 1234` matches nothing.
- **RC3 Surname search is non-deterministic.** `take: 20, orderBy: { lastName: 'asc' }` with no tie-break (`customers.service.ts:56-57`): a surname with 44 rows returns an arbitrary 20.
- **RC4 Plate normalisation is asymmetric.** Imports store `plateNumber` stripped/uppercase; UI create stores it verbatim and only `vehicleCode` is stripped (`vehicles.service.ts:79-87`). `/customers` and `/vehicles` survive via a `vehicleCode` fallback; global search has none (`search.service.ts:80-84`), so `1234 AB` fails there, and any ≥4-digit query also fires a phone branch that returns false-positive customers.
- **Ruled out:** scope helpers (`liveCustomerWhere` excludes only the placeholder and test rows — imported customers ARE searchable), validation, 404s. No trigram/GIN indexes exist (all predicates are `ILIKE '%q%'` seq scans — a scaling note at ~7k rows, not the cause).

### C2. Inspection templates — why the deployed site lacked them despite parity work
- **The repository at HEAD reproduces both templates.** Fresh DB `bsop_golive_probe`: `prisma migrate deploy` → `db:seed` (prints `Inspection template v1: 30 items… (active=true)`) → `deploy-check` **PASS** (`vehicle inspection template — 1 active`, `pre-inspection template — 1 active`, `checklist items — 30`), and the exact runtime lookup (`inspections.service.ts:116-124`: `isActive, kind`, highest version, VEHICLE_INSPECTION needs ≥1 item on that row) finds both kinds. Templates carry no `siteId`, so site mismatch is impossible.
- **Therefore the deployed database was never seeded by the current build command.** Seed and deploy-check run only in `render.yaml` `buildCommand` (`:32`); `startCommand` (`:34`) only migrates. The two states consistent with the symptom: (1) the `bsop-api` service's dashboard **Build Command is detached from `render.yaml`** (the service was created from the CR-054 blueprint whose build had no seed; `AGENTS.md:49-50` already warns about this; docs/80 recorded the identical July incident), so deploys migrate but never seed; or (2) the free-tier Postgres was **replaced/restored after the last build** (`DEPLOY_RENDER.md:57-59`), which the start command's migrate silently accepts.
- **Why parity did not catch it:** deploy-check runs only inside the build; its item check sums across all active versions while runtime reads only the top one; `/health` `referenceDataSeeded` is kind-agnostic; the fresh-clone smoke (docs/119 §G.8) counted rows but never `POST /inspections`; it validated a local fresh clone, never the Render database.
- **The Job Sheet works because it is code-defined** (`JobSheetDraft`, one JSON document per visit — no template). Latent bug: the hub's "Job Sheet" picker `POST`s `/inspections` and would also throw.

### C3. Email — why it was not delivered
- **F1 Body-less email paths fail at the provider.** `SmtpNotificationProvider` refuses any message without a pre-rendered body (`smtp.provider.ts:44-47`, "Empty email body"). Only the composer and the CR-105c booking messages render a body; pickup-ready, the 24-hour reminder sweep, the midday follow-up and maintenance reminders pass a `templateKey` only, and there is no email renderer (the Twilio provider renders SMS from the key; SMTP has no equivalent).
- **F3/F4/F6 Misleading success.** `sendPickupReady` returns `status: 'SENT'` hard-coded (`notifications.service.ts:511, :530`) and the pickup panel prints "Email Sent" on any 2xx; maintenance marks the reminder SENT regardless of the log (`maintenance-reminder.service.ts:241-247`); history renders a green **SENT** badge for stub-simulated rows with only a faint "not delivered" tag; the composer closes on any 2xx without per-channel results; Admin → Deployment shows only the SMS provider.
- **Configuration/transport causes the code allows:** a boot throw when `EMAIL_PROVIDER=smtp` with `SMTP_HOST`/`SMTP_FROM` missing or `SMTP_SECURE` not literally `true|false` (Render then keeps the previous instance running the stub), port/`secure` mismatch, no connection timeouts (a wrong port holds the request up to 2 min), `info.rejected` ignored, `From` ≠ authenticated mailbox. Decision table by `notification_logs` (`simulated`/`provider_reference LIKE 'stub-%'` → stub still running; `FAILED 'Empty email body'` → F1; `FAILED` with SMTP text → transport; `SENT` with real message-id → mailbox-side).

### C4. External links — why they were internal-network-only
- **There is no public base URL anywhere** (`env.ts`, `.env.example`, `render.yaml`, `deploy-check`). The API returns the status link as a **relative path** (`check-in.service.ts:450`, `walk-ins.service.ts:425`) and the web prefixes **`window.location.origin` — the staff PC's own address** (`check-in/page.tsx:330`, `appointment-detail-modal.tsx:188`, `queue/[id]/page.tsx:645-648`). A LAN/localhost origin therefore becomes the link handed to the customer. The booking manage link borrows the **first CORS origin** as a stand-in (`public-booking.service.ts:668-672`, reading `process.env` directly). Public pages then call the API via `NEXT_PUBLIC_API_URL` or `hostname:3001` — so an unset build-time value breaks them on Render too. No notification template carries the status link at all.

### C5. Appointment wizard — what prevented changing Customer/Vehicle
- The page is a step wizard (`appointments/new/page.tsx:42,106`) but **the only backward transition is Time → Services** (`:530-535`); step circles are not clickable; the customer/vehicle labels are plain text.
- **Auto-advance effect bounces any "back" forward again**: `useEffect` (`:182-192`) runs whenever `customerDetailQuery.data` is present and `step === 'customer'`, so returning to the customer step with a customer still selected immediately pushes the user to Vehicle/Services.
- **Selecting a customer resets nothing downstream** (`:346` sets only `selectedCustomer`) — vehicle, services, notes, date/time all survive; a one-vehicle customer silently overwrites the vehicle. The check-in page does this correctly (`check-in/page.tsx:220-241`, visible **Change** button `:406`); the wizard has no equivalent.
- Also: `?vehicleId` deep link is never read; time is a free `<input type="time" min="08:00" max="17:00" step="900">` with rule values in the UI; **no staff availability endpoint exists** — only the public one — so staff never see the engine's slots.

### C6. SharePoint records — why they were not present after the expected migration
- **The SharePoint Contact Database import is provably complete locally**: 7,157/7,157 rows → 6,856 customers (301 rows merged into 237 multi-vehicle owners by name+phone) and 7,157 vehicles, 0 missing, 0 dangling refs (`ExternalSystemRef` batch `10b5c669…`, 2026-06-09).
- **But a second customer source has never been imported and has no importer**: `Customer_List_Master.xlsx` (2026-06-15, 8,851 rows) = 7,158 "Existing" (100% present in the DB by phone/plate/VIN/email) + **1,693 "Peachtree (new)"** accounting customers with **0 %** presence in the database. The owner's "records not carried over" most plausibly refers to this merged master list, not the SharePoint list alone.
- **Whether the deployed database ever received the import cannot be determined from this machine**: operational data reaches Render only by an operator running the import from a laptop against the External Database URL (`DEPLOYMENT.md §6`); the free-tier Postgres expires and is recreated (`DEPLOY_RENDER.md:57`), which silently erases an import; `deploy-check` only warns when customers = 0, so a partial import passes.
- **Tooling gaps:** no reconciliation output (commit prints only totals; matched/created/rejected never split), rows dropped silently by the parser (`import-customers.ts:55,61`), customer provenance only in a `notes` string (only vehicles get `ExternalSystemRef`), no `ImportRun` record, and 1,089 historical jobs sit on the hidden placeholder customer.

## D. Fix design (summary — details in the implementation records)

| Area | Fix | Gate |
|---|---|---|
| Search | One pure parser + one shared where-builder (tokenised names, either order, across first/last; digits-only phone on both sides with write-side normalisation + backfill of the 3 dashed rows; plate/VIN normalisation; deterministic order; `take 50` + `truncated`); used by `/customers`, directory, `/vehicles`, `/search`; grouped, de-duplicated global results | data-format change (phone/plate storage) → CR |
| Templates | Seed asserts the runtime predicate per kind; runtime lookup requires items for VEHICLE_INSPECTION; `deploy-check` **Required Form Configuration** (Job Sheet / Pre-Job Inspection / Service Inspection, FAIL) also run at **start**; `/health` per-form flags; hub picker fix; operator runbook | none |
| Email | Server-side email rendering for every legacy template key; honest status states (Queued/Sending/Sent/Delivered/Failed/Test Redirected/Simulated) in API projection + history/composer/pickup UI; `accepted/rejected` honoured; SMTP timeouts; `POST /notifications/verify` (transport verify + real test send, logged); Admin → Deployment shows email provider + mode | none |
| Links | `PUBLIC_APP_URL` (validated env, prod-required in deploy-check, must not be localhost/private); one `publicUrl()` helper; API returns absolute `customerStatusUrl`; web stops using `window.location.origin`; manage links via helper; web build fails on Render without `NEXT_PUBLIC_API_URL` | AG-07 (customer-facing exposure unchanged: same tokens) |

## E. Assumptions
1. The deployed database will be brought to parity by the owner running the documented bootstrap (seed + check) against the External Database URL, or by re-syncing the Render Blueprint; this CR makes the failure detectable at start and in `/health`, and gives the exact steps.
2. `PUBLIC_APP_URL` is set on Render to the public `bsop-web` URL by the owner (it cannot be inferred from the request).
3. The 3 PM cutoff applies to customer self-service only; staff remain exempt unless `staff_latest_start_enforced` is switched on (then explicit, audited override).
4. Peachtree-only customers (1,693) are **not** imported by this CR; the reconciliation report surfaces them for a decision.
5. External-network testing of links from a phone must be performed by the owner; this CR verifies that generated links use the configured public base and that public pages work when reached by a non-localhost host.
